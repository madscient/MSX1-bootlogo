# 技術仕様

MSX1 起動ロゴ ROM の仕様・設計・検証状況をまとめた、開発者向けの資料です。使い方とビルドの手順は [README](../README.md) にあります。

この資料のうち、ROM 自身の動作（何をどこに書くか、どの順で処理するか）は、ソースコードと検証プログラムで確かめられる内容です。MSX 本体・BIOS・特定の機種の挙動についての記述は、エミュレータ（openMSX、blueMSX）で確かめたものと、確かめていないものがあります。実機では確かめていません。確認の状況は「[検証状況](#検証状況)」にまとめています。

## バイナリ仕様

同じソースから、配置アドレスだけが違う 2 つのイメージを作ります。

| イメージ | 配置 | ヘッダ | INIT |
|---|---|---|---|
| `msx_logo_page1.rom` | 4000h–7FFFh（ページ 1） | `41 42 10 40 00 00 00 00 00 00 00 00 00 00 00 00` | 4010h |
| `msx_logo_page2.rom` | 8000h–BFFFh（ページ 2） | `41 42 10 80 00 00 00 00 00 00 00 00 00 00 00 00` | 8010h |

- Z80、MSX1 の Graphics II（SCREEN 2）、256×192、VRAM 16KB。
- サイズはどちらも 16,384 バイト。マッパー不要。コードとデータのあとは FFh で埋めます。STATEMENT / DEVICE / TEXT はすべて 0。
- 2 つのイメージの違いは配置アドレスだけです。バイナリで違うのは、アドレスの上位バイトにあたる 113 バイトで、どれも 40h の差です。処理の内容は同じです。
- メイン BIOS が page 0、RAM が page 3 にある標準の MSX 起動環境を前提にします。RAM は 8KB（E000h–FFFFh）あれば動作します。
- INIT は BIOS から渡されたスタックをそのまま使い、RET で BIOS の ROM 検索へ戻ります。常駐フックや強制リセットは使いません。
- 画面の初期化は BIOS の CHGMOD で行います。アニメーションの間は割り込みを許可し、BIOS のフレームカウンタ（JIFFY）を時間の基準にします。
- ROM がもう一方のページにも見える（ミラーされる）構成には対応しません（「[ミラーされる構成](#ミラーされる構成)」）。

## 画面

| 領域 | VRAM |
|---|---|
| パターン | 0000h–17FFh |
| 名前 | 1800h–1AFFh |
| スプライト属性 | 1B00h–1B7Fh |
| 色 | 2000h–37FFh |
| スプライトパターン | 3800h–38BFh（16×16 を 6 個） |

- ロゴは x=47–212、y=53–101。黒い矩形は x=32–223、y=44–111。
- RAM 容量の表示は x=64、y=120 から 15 文字（8 ドット幅）。
- 色テーブルは F1h（白/黒）で始め、上から 8 走査線ずつ F4h（白/青）に変えます。ロゴ周囲の矩形は F1h のまま残します。矩形の上端はタイルの途中（y=44）なので、その 8 走査線だけは下の 4 走査線を残します。最後に画面外のボーダーも R7=04h（dark blue）にします。
- レーザーは、縦と斜めのものをスプライトで、横のものをパターンで描きます（「[レーザーと輪郭の描画](#レーザーと輪郭の描画)」）。
- スプライトは 16×16、拡大なしで使います。VDP の R1 にあるスプライトの大きさと拡大の設定は、INIT に入った時点の値を覚えておき、終了時に戻します。

## 作業 RAM

E000h–E05Fh を使います。これ以外の RAM には書き込みません（スタックと、RAM 容量の検査地点は除きます）。

- E000h は、RAM が 8KB の機種にもある範囲（E000h–FFFFh）の先頭です。
- 呼び出し元である BIOS のスタックは page 3 の高位側にあるので、作業領域をそこから離しています。INIT に入った時点のスタックポインタは、openMSX 上の純正 BIOS の 5 機種で F08Eh、C-BIOS 0.29 で F2ECh でした。
- アドレスは、ソースの定数 `work` からの相対で定義しています。検証スクリプトはアドレスをシンボルから読みます。

| アドレス | 用途 |
|---|---|
| E000h | 各段階の進行カウンタ |
| E001h | レーザーの色の番号（0–2） |
| E002h | 色を次に切り替える締切（JIFFY の下位バイト） |
| E003h | 処理中の横のレーザーの色コード |
| E004h | 100ms あたりのフレーム数（60Hz: 6、50Hz: 5） |
| E005h | 次の締切（JIFFY の下位バイト） |
| E006h–E007h | 次に読むシナリオのアドレス |
| E008h–E009h | 表示中のシナリオのアドレス（色の切り替え用） |
| E00Ah | 50Hz 用の端数の繰り越し |
| E00Bh | レーザーの区間の印（1 の間は 100ms 間隔で、色を切り替える） |
| E00Ch–E00Dh | 表示中の横のレーザーのデータのアドレス（色の切り替えと消去用） |
| E00Eh | INIT に入った時点の、スプライトの大きさと拡大の設定 |
| E00Fh | 横のレーザーの処理の種類（描画、色の切り替え、消去） |
| E010h | 処理中の横のレーザーの、最後のバイトのマスク |
| E011h | 主 RAM のスロット ID |
| E012h | 検出した RAM 容量（KB） |
| E013h–E014h | フォントのアドレス |
| E015h–E017h | 主 RAM のスロットの page 0–2 を、それぞれどの方法で読み書きするか |
| E018h | 主 RAM がある主スロットの、副スロットレジスタの値 |
| E019h | 同じ値のうち、page 0 だけを主 RAM の副スロットに変えたもの |
| E01Ah–E01Ch | 3 本のレーザーそれぞれの、現在の色コード |
| E020h–E024h | 検査地点の元データ |
| E028h–E02Ch | 検査地点ごとの結果 |
| E040h–E05Fh | タイル列ごとの「輪郭が出現済み」フラグ（32 列） |

INIT の最後に E000h–E05Fh をすべて 0 に戻してから RET します。

画面の内容を RAM に写して持つことはしません。

## 時間の管理

- BIOS 002Bh の bit 7 で 50Hz / 60Hz を判定します。
- 更新の基本単位は 50ms です。60Hz では 3 フレーム、50Hz では 2 フレームと 3 フレームを交互に使って平均 50ms にします。
- レーザーの区間だけは 100ms 単位（60Hz で 6 フレーム、50Hz で 5 フレーム）で、36 段階です。
- 各段階は「前の締切＋間隔」まで HALT で待つ方式なので、描画にかかった時間は間隔に含まれます。
- レーザーの色は、レーザーの区間が始まった締切から数えて 2 フレームごとに、白（15）、ライトイエロー（11）、シアン（7）の順で切り替えます。同時に出る 3 本は、この順番の中で 1 つずつずれた色になります（1 本目が白なら、2 本目はライトイエロー、3 本目はシアン）。3 本が同じ色になることはありません。こちらも締切を 2 フレームずつ進める方式で、待っている間のフレームごとに締切を調べ、過ぎていれば表示中のレーザーの色を書き換えます。フレーム数で数えるので、色が変わる速さは 60Hz と 50Hz で異なります。
- ロゴの完成までが 114 段階で 7.5 秒、RAM 容量の表示が 40 段階で 2 秒です。RAM 容量の検査と文字の描画を終えてから締切を取り直すので、検査にかかる時間は 2 秒に含まれません。
- NTSC の厳密な走査周波数などにより、実時間にはわずかな差が出ます。

## レーザーと輪郭の描画

- シナリオは 1 段階ごとに、輪郭を出現させるタイル列（なければなし）と、レーザー 3 本ぶんのデータを持ちます。レーザーは長さ 67 ドットの線分で、画面の外にはみ出した部分は表示されません。3 本には 0–2 の番号があり、色はこの番号ごとに決まります。2 本のスプライトのレーザーが交わる点では、番号の小さいほうが手前に出ます。
- 輪郭と塗りつぶしは、ROM 内の画像からタイル列（8 ドット幅 × 画面の高さ）単位で VRAM へ写します。輪郭は列 4–27 を決まった順で、塗りつぶしは列 4 から 27 へ順に写します。
- 縦と斜めのレーザーはスプライトで表示します。16 走査線ごとに 1 枚、1 本につき最大 5 枚を縦に並べるので、1 本のレーザーが 1 本の走査線で使うスプライトは 1 枚です。3 本あわせても 3 枚で、1 走査線に 4 枚までという VDP の制限に収まります。画面の左端からはみ出すスプライトは、アーリークロック（32 ドット左へずらす指定）で表示します。スプライトの位置は生成時に計算してシナリオに入れてあり、ROM は属性テーブルへ写すだけです。
- 横のレーザーはパターンに描きます。67 ドットの横線は 1 本の走査線に 5 枚のスプライトが必要で、制限を超えるためです。バイト単位（8 ドット）で書き、次の段階の前に消します。下にあるはずの内容は、その列の輪郭が出現済みなら ROM の輪郭画像のバイト、未出現なら 0 です。
- 横のレーザーの色は色テーブルで指定します。色テーブルは 8 ドット × 1 走査線ごとに 1 バイトなので、レーザーと同じバイトにある輪郭のドットは、レーザーが表示されている間はレーザーの色になります。該当するのは、レーザーの両端のバイトにある、レーザーと同じ走査線上のドットだけです。
- 1 つの段階の中で 2 本の横のレーザーが同じバイトを使うことは、ROM では扱いません。生成時に検査し、該当すればエラーにします。

## VDP への書き込み

VRAM への直接書き込みは、アドレス 2 バイトとデータの全体を DI / EI で囲みます。途中で割り込みが入ると、BIOS の割り込み処理がステータスを読んで VDP のアドレスラッチを戻してしまうためです。

連続したアドレスへ続けて書くとき（輪郭の 1 タイルぶんの 8 バイト、スプライト属性）は、アドレスを 1 回だけ設定してデータを続けて書きます。このときデータは 1 バイトずつサブルーチンを呼んで書き、書き込みの間隔を VDP が必要とする 8 マイクロ秒（29 T ステート）より長く保ちます。

## ミラーされる構成

16KB の ROM は、エミュレータの設定や単純なカートリッジ基板によっては、もう一方のページ（ページ 1 用なら 8000h–BFFFh、ページ 2 用なら 4000h–7FFFh）にも同じ内容が見えます。BIOS の ROM 検索は各スロットの 4000h と 8000h の両方で AB 署名を調べるので、この構成では INIT が 2 回呼ばれます。

この ROM は、2 回目の呼び出しを見分けません。呼ばれるたびに再生するので、アニメーションが 2 回再生されます。ミラーされる構成での動作は保証しません。

- openMSX と blueMSX は、16KB の ROM を自動でこの構成にします。ミラーなしにするには、ROM タイプを指定します。openMSX では `Normal4000`（ページ 1 用）または `Normal8000`（ページ 2 用）、blueMSX では「Normal 4000H」（ページ 1 用）または「BASIC ROM」（ページ 2 用）です。
- ミラーがあっても INIT を 1 回しか呼ばない BIOS（openMSX 21.0 の C-BIOS 0.29）では、1 回だけ再生されます。

同じスロットのもう一方のページに別の ROM がある構成は、ミラーではないので問題なく動作します。ただし C-BIOS 0.29（MSX1）は、ページ 1 に別の ROM があるとページ 2 の ROM の INIT を呼ばないので、この構成ではページ 2 用のイメージは再生されません。

## RAM 容量の検査

page 3 に選択されている主 RAM のスロットについて、16KB のページ 4 つと、page 3 の上半分を調べます。

- 主スロットは RSLREG、拡張の有無は EXPTBL から求めます。
- 副スロットは、page 3 から見える FFFFh（副スロットレジスタの反転値）を直接読んで求めます。BIOS が持つ副スロットレジスタの写し（SLTTBL）は使いません。写しが page 3 の実際の選択と合っていない環境では別の副スロットを指してしまい、その状態で RDSLT / WRSLT を呼ぶと BIOS が page 3 を切り替えて、スタックと作業領域のある RAM が見えなくなるためです。
- 0100h / 4100h / 8100h / C100h / E100h に、地点ごとに異なる検査値を 2 回書いて読み戻します。
- 地点ごとに値を変えるので、ミラーされた領域は 1 回しか数えません。2 回とも合った地点だけを RAM とするので、ROM や空き領域は数えません。
- page 3 は、C100h が RAM なら 16KB、そうでなく E100h が RAM なら 8KB と数えます。E100h を最後に書くので、C000h–DFFFh が E000h–FFFFh のミラーである場合は C100h が合わず、8KB になります。
- 検査の前に 5 地点の元データを保存し、検査のあとに戻します。検査中は割り込みを禁止します。
- RAMAD0–3 は使いません。ディスクのない MSX1 では設定されている保証がないためです。

page 3 の 2 地点は直接読み書きします（page 3 にスロット間呼び出しを使わない理由は上と同じです）。page 0–2 の読み書きの方法は、主 RAM のスロットによって変えます。

| 主 RAM のスロット | page 0 | page 1 | page 2 |
|---|---|---|---|
| スロット 0 以外 | RDSLT / WRSLT | RDSLT / WRSLT | RDSLT / WRSLT |
| BIOS と同じスロット（スロット 0、または拡張されたスロット 0 の副スロット 0） | 調べない | 調べない | RDSLT / WRSLT |
| 拡張されたスロット 0 の、BIOS とは別の副スロット | ROM が副スロットを切り替えて直接読み書きする | RDSLT / WRSLT | RDSLT / WRSLT |

- BIOS と同じスロットでは、page 0 と page 1 は BIOS と BASIC の ROM なので RAM ではありません。ここは調べず、システム ROM には書き込みません。本物の ROM は書き込みを無視しますが、エミュレータの機種定義がシステム ROM を「書き込みに反応するマッパー」として登録していると、検査値の書き込みで BIOS のバンクが切り替わり、暴走します。
- 拡張されたスロット 0 の別の副スロットにある RAM の page 0 に RDSLT / WRSLT を使うと、BIOS が page 0 の副スロットを切り替えた時点で、page 0 で動いている BIOS 自身が見えなくなり、暴走します。この page だけは、割り込みを禁止したまま ROM が副スロットレジスタ（FFFFh）の page 0 のぶんを主 RAM の副スロットに変え、0100h を直接読み書きして、すぐに元の値へ戻します。切り替えている間は BIOS を呼びません。
- BIOS のスロットは、EXPTBL の先頭（FCC1h）から求めます。

## RAM 容量の文字表示

`Main RAM : ##KB` は本体のシステムフォントで表示します。8KB のときは `Main RAM :  8KB` と、数字を右に寄せます。文字列は ROM 内に ASCII で持ち、各文字の 8×8 パターンをフォントから SCREEN 2 のパターンテーブルへ LDIRVM で転送します。

フォントの場所は、CGPNT（F91Fh–F921h）がメイン ROM のスロットを指していればそのアドレス、そうでなければメイン ROM の 0004h（CGTABL）が指すアドレスです。

## 終了処理と BASIC への復帰

RAM 容量を 2 秒表示したあと、スプライトの大きさと拡大の設定を INIT に入った時点の値に戻し、SCREEN 1（前景 15、背景と周辺 4）にして、作業 RAM を消去して RET します。BIOS の ROM 検索がそのまま続き、そのあと BASIC が起動します。

## 内蔵ソフトを持つ機種

Sony HB-11 は、カートリッジがなくても BASIC ではなく内蔵ソフトが起動する機種です。この ROM を挿した場合も、アニメーションのあとに内蔵ソフトが起動します。openMSX 21.0 の HB-11（主 RAM は副スロット 3-2）で、RAM 容量が 64KB と表示されること、INIT から戻ったあと画面が SCREEN 2 になり、page 1 に内蔵ソフトのスロット 3-0 が選択されていることを確認しています。カートリッジなしで起動した場合も同じ状態になります。

以下は**未検証**です。根拠となる測定の記録はリポジトリになく、確かめていません。

- 内蔵ソフトが起動する仕組み: 内蔵ファームウェアが INIT で H.STKE に「スロット 3-0 の 5E60h を呼ぶ」フックを設定する（スロット番号 83h が固定で書かれている）。
- ファームウェアを 3-1、RAM を 3-0 に置いたエミュレータのマシン定義では、フックが RAM の 5E60h に飛ぶ。この場合の動作は ROM 側では回避できない。

## アセット

`assets/` の 4 ファイルは `tools/gen_assets.py` の出力で、手で編集するものではありません。ROM の内容が Python の疑似乱数の実装に左右されないように、生成結果をリポジトリに入れています。

| ファイル | 形式 |
|---|---|
| `outline.dat`、`solid.dat` | SCREEN 2 のパターンテーブルと同じ並びの 6,144 バイト。点 (x, y) は、オフセット (y÷8)×256 + (x÷8)×8 + (y mod 8) のバイトの、bit 7 を左端とするビット |
| `sprites.dat` | 16×16 のスプライトパターン（32 バイト）が 6 個。順に、右下がりの斜線、左下がりの斜線、縦線、それぞれの終端用（上の 3 走査線だけ） |
| `beams.dat` | 段階ごとの可変長のレコードが 36 個。下の表のとおり |

`beams.dat` の 1 レコード:

| 内容 | バイト数 |
|---|---|
| スプライトの数（0–15） | 1 |
| スプライトごとに、Y、X、パターン名。VDP の属性テーブルに書く値。パターン名のバイトは、bit 7 がアーリークロック、下位 2 ビットがレーザーの番号（16×16 のスプライトでは、VDP はパターン名の下位 2 ビットを無視する） | 3 × 数 |
| 輪郭を出現させるタイル列（255 はなし） | 1 |
| 横のレーザーの数（0–3） | 1 |
| 横のレーザーごとに、レーザーの番号、最初のバイトのパターンテーブル内オフセット（下位、上位）、バイト数、最初のバイトのマスク、最後のバイトのマスク | 6 × 数 |

- ロゴは多角形の頂点列として持ち、480×424 の座標を 256×192 に縮小して塗りつぶします。輪郭は、塗りつぶしのうち上下左右のどれかが外側である点です。
- レーザーの向きと始点、輪郭の出現順は、固定シードの疑似乱数から決めます。
- レーザーは 67 ドットで 16 の倍数ではないので、各レーザーの最後のスプライトは終端用のパターン（3 走査線）です。
- 横のレーザーのバイトは 8 ずつ離れています。バイト数が 1 のときは、2 つのマスクに同じ値（両端を合わせたもの）が入っています。

```text
python tools/gen_assets.py          4 ファイルを書き出す
python tools/gen_assets.py --check  書き出さずに比較し、違いがあれば終了コード 1
```

標準ライブラリだけで動きます。Python の疑似乱数の実装に依存するので、別のバージョンの Python で同じ結果になるかは `--check` で確かめてください（確認済みなのは Python 3.13.14 だけです）。

## ビルド

`python tools/build.py` でビルドします。使い方は [README](../README.md#ビルド) にあります。

- スクリプトは、リポジトリのルートでイメージごとにアセンブラを実行し、できたイメージ（配置アドレスから `rom_end` まで）の後ろを FFh で埋めて 16,384 バイトにします。イメージの大きさが `rom_end` と合わないとき、16KB を超えるとき、配置アドレスがスクリプトの表と合わないときは、エラーで止まります。
- イメージごとに `src/page1.asm`、`src/page2.asm` をアセンブルします。この 2 つは配置アドレス `rom_base` を定義して、本体の `src/logo.asm` を取り込むだけです。アセンブラのコマンドラインから値を渡す方法は 3 つのアセンブラで共通にできないので、ソースを分けています。
- 埋め草をソースに書かないのは、zmac が `ds` の埋め値に 128 以上を受け付けないためです。
- ソースは zmac、sjasmplus、Pasmo の 3 つが受け付ける構文だけで書いています。
- `include` と `incbin` のパスはリポジトリのルートからの相対パスです。3 つとも追加のオプションなしで解決できる書き方にしています。
- アセンブラごとに形式の違うシンボルの一覧を読み、イメージごとに `build/symbols_page1.json`、`build/symbols_page2.json`（ラベルと定数の名前と値）にまとめます。2 つの検証スクリプトはこのファイルを読みます。

出力（`build/` 以下、N は 1 と 2）: `msx_logo_pageN.rom`、`symbols_pageN.json`、アセンブラの出力（`msx_logo_pageN.cim` は埋める前のイメージ。`msx_logo_pageN.lst`、`msx_logo_pageN.sym` はアセンブラによってある場合とない場合があります）。

## リリース

リリースには `msx_logo_page1.rom` と `msx_logo_page2.rom` の両方を同梱します。同梱する前に、ビルドした 2 つのイメージの SHA-256 が「[検証状況](#検証状況)」の値と一致することを確かめます。

## 検証プログラム

2 つあります。`tools/verify.py` は BIOS を持たない小さな模擬環境で、細かい構成を数多く試せます。`tools/test_openmsx.py` は openMSX の上で、本物の BIOS 実装と一緒に動かします。どちらも 2 つのイメージを順に確かめ、`--page` で片方だけにできます。

レーザーの区間の画面の期待値は、`tools/gen_assets.py` が持つレーザーの形（位置と向き）から `tools/screen.py` が組み立てます。`beams.dat` のバイト列からは組み立てないので、この比較は `beams.dat` の符号化と、それを読む ROM の処理の両方を確かめます。スプライトは、属性テーブルとパターンから VDP の表示規則（16×16、アーリークロック、1 走査線に 4 枚まで）で画素に直して比べます。

### 模擬環境での検証

`tools/verify.py` は、ビルドした ROM の Z80 命令を実行し、BIOS の呼び出しを代わりに処理する検証用のプログラムです。MSX 全体のエミュレータではありません。検査に 1 つでも通らなければ、エラーで止まります。

検査する内容:

- ROM のサイズ、AB 署名、INIT のアドレス、コードとデータが 16KB に収まること。作業 RAM が E000h 以上にあること。
- 50Hz と 60Hz のそれぞれで全体を実行し、段階の数（154）、各段階が締切どおりであること、ロゴ完成までの時間、RAM 容量の表示が 2 秒であること。50Hz の実行は、RAM 8KB が BIOS と同じスロット 0 にある構成で行います。
- レーザーの区間の全フレームで、パターン、色、スプライトが期待値と一致すること（3 本が別々の色で、2 フレームごとに切り替わることを含む）。1 段階ぶんの処理が 1 フレームの長さに収まること。
- 輪郭が完成した時点のパターンが `outline.dat` と一致すること、最終のパターンが `solid.dat` と RAM 容量の文字に一致すること。
- 色テーブルの最終状態、青い領域が上から 1 段ずつ増えること、黒い矩形が保たれること、R7 が 04h であること。
- VRAM への直接書き込みが、パターン、色、スプライト属性のテーブルの範囲に収まること。書き込みのときに割り込みが禁止されていること。書き込みの間隔が 29 T ステート以上であること。名前テーブルが標準の並びのままで、最後にスプライトが無効になっていること。
- スプライトの大きさと拡大の設定が、終了時に元の値へ戻ること。
- 主 RAM をスロット 3、副スロット 3-2、スロット 0（BIOS と同じスロット）、副スロット 0-0、副スロット 0-2 に置き、8 / 16 / 32 / 48 / 64KB と 8 / 16 / 32KB ミラーの構成で、容量が正しいこと、検査地点の元データが戻ること。
- page 3 に RDSLT / WRSLT を使わないこと。BIOS がある主スロットの page 0 に RDSLT / WRSLT を使わないこと。BIOS と同じスロットの page 0 と page 1 を読み書きしないこと。BIOS を呼ぶ時点で page 0 に BIOS が見えていること。副スロットレジスタへの書き込みが page 1–3 の選択を変えず、終了時に元の値へ戻っていること。
- RAM のない番地へ書き込まないこと（8KB の構成での C000h–DFFFh。検査地点の C100h を除く）。
- 終了時に作業 RAM が 0 に戻っていること、作業 RAM 以外の RAM（C000h–F2FFh）が書き換えられていないこと、スタックポインタと呼び出し元のスタックの内容が保たれていること。
- 2 つのイメージが、全フレームで同じ画面を出すこと。

限界:

- 実装している Z80 命令と BIOS 呼び出しは、この ROM が使うものだけです。それ以外に出会うとエラーで止まります。
- BIOS は代替処理で、純正 BIOS のコードは実行しません。フォントも代用です。
- 命令の実行時間は数えますが、割り込み処理の時間、M1 ウェイト、VDP の競合は再現しません。処理時間と書き込み間隔の数値は、この条件での値です。
- 検査するのは実行した結果です。実行時に参照されない ROM のバイトが変わっても検出しません。ビルド結果が同じかどうかは SHA-256 で比べてください。

出力（`build/` 以下）: `verification.json`。Pillow がある場合は加えて `preview.gif`、`final.png`、`frame_*.png`、`storyboard.png`。GIF は RAM 容量の表示までの 9.5 秒を繰り返す形で、BASIC の画面は含みません。60Hz の実行のフレームごとの画面から作るので、レーザーの色の切り替えも入ります。

### openMSX での検証

`tools/test_openmsx.py` は、ビルドした ROM をカートリッジとして openMSX を起動し、ブレークポイントで機械の状態を記録して（`tools/openmsx_test.tcl`）、その記録を検査します。openMSX は環境変数 `OPENMSX_DIR` のフォルダから、なければ PATH から探します。

- ウィンドウを開かず、最高速で実行します。16 通りの構成を 2 つのイメージで試して 30 秒ほどです。
- openMSX のユーザーデータと保存データのフォルダを `build/openmsx/` に切り替えて起動するので（環境変数 `OPENMSX_USER_DATA` と `OPENMSX_HOME`）、利用者自身の openMSX のファイルは読み書きしません。
- ROM は、ミラーなしの ROM タイプ（`Normal4000` / `Normal8000`）で挿入します。
- RAM の配置を変えた機種は、openMSX に付属する機種定義から派生させて `build/openmsx/` に作ります。元の機種の RAM を取り除き、指定したスロットに指定した容量の RAM を置きます。主スロットに副スロットを足す場合、もとからあった装置は副スロット 0 に入れます。

試す構成（機種はどれも C-BIOS_MSX1。50Hz だけ C-BIOS_MSX1_EU）:

| 構成 | 主 RAM |
|---|---|
| 60Hz | 64KB、スロット 3（機種のまま） |
| 50Hz | 64KB、スロット 3（機種のまま） |
| リセット 1 回 | 64KB、スロット 3（機種のまま） |
| 副スロット 3-2 | 64KB、48KB |
| 副スロット 3-1 | 16KB、8KB |
| スロット 3 | 32KB、16KB、8KB |
| スロット 0（BIOS と同じスロット） | 16KB、8KB |
| 副スロット 0-2（BIOS は副スロット 0-0） | 64KB、48KB、16KB、8KB |

起動のたびに検査する内容:

- INIT が呼ばれ、呼び出し元へ戻ること。戻ったときにスタックの内容が保たれていること。page 3 の RAM のうち、作業 RAM より下と、作業 RAM の上からスタックの手前までが書き換えられていないこと。
- スプライトの大きさと拡大の設定（VDP の R1 と、BIOS が持つその写し）が、INIT の前後で同じであること。
- アニメーションがちょうど 1 回再生されること（段階の数が 154）。
- ロゴ完成までの時間と、RAM 容量を表示している時間が、フレーム数で合っていること。
- レーザーの各段階が終わる時点の画面（パターン、色、スプライト）が期待値と一致すること。
- レーザーの区間の全フレームで、スプライトと、横のレーザーの色が期待値と一致すること（3 本が別々の色で、2 フレームごとに切り替わること）。
- レーザーの区間のすべてのフレームで、そのフレームのうちに処理が終わって HALT に達していること。
- 主 RAM のスロットの判定と RAM 容量が、ROM を通さずに openMSX から読んだ値と一致すること。
- RAM の検査地点の内容が、検査の前後で同じであること。
- 最終画面のパターンが `solid.dat` と、BIOS のフォントで描いた RAM 容量の文字に一致すること。色、名前テーブル、スプライトの終端、R7。
- 終了時に作業 RAM がすべて 0 であること。
- INIT から戻って 6 秒後に、CPU がカートリッジの外を実行していること。

`--machine 機種名` を付けると、上の構成の代わりに openMSX のその機種で 1 回（リセット 1 回つき）試します。純正 BIOS の機種を試すにはそのシステム ROM が必要です。openMSX 本体の `share/systemroms` に加えて、環境変数 `MSX_ROM_DIRS` に並べたフォルダ（PATH と同じ区切り）から探します。ROM は SHA-1 で照合されるので、openMSX の機種定義が求めるものと同じ内容のファイルでなければ見つかりません。

`--machine` には次のものを足せます。

| オプション | 内容 |
|---|---|
| `--ram スロット:容量` | その機種の RAM を、指定の配置に置き換えて試す。例: `--ram 0-2:64`（副スロット 0-2 に 64KB）、`--ram 3:16` |
| `--rom alone`（既定） | カートリッジのスロットのもう一方のページは空き |
| `--rom neighbour` | もう一方のページに別の ROM を置く。INIT がすぐに戻るだけの ROM を、検証スクリプトがイメージと並べて 32KB の ROM にする |
| `--rom mirrored` | openMSX に ROM タイプを選ばせる（16KB の ROM はミラーされる）。保証しない構成で、INIT を 2 回呼ぶ BIOS では「ちょうど 1 回再生される」の検査が不合格になる |

検査のうち「INIT から戻って 6 秒後」の画面の文字は、合否には使わず結果に記録します。純正 BIOS の機種では、ここに BASIC の起動メッセージと `Ok` が記録されます。INIT に入った時点のスタックポインタ、BOTTOM、HIMEM も結果に記録します。

限界:

- 既定の構成はすべて C-BIOS です。C-BIOS には BASIC がないので、BASIC のプロンプトまで確かめるには `--machine` で純正 BIOS の機種を指定します。
- エミュレータ上の確認であり、実機の確認ではありません。
- 画面は VRAM の内容で確かめます。ウィンドウを開かないので、表示された画像そのものは見ていません。
- 「スタックの手前まで」は、INIT に入った時点のスタックポインタの 256 バイト下までです。
- 主 RAM の容量を openMSX から読むとき、16KB のページごとの装置名に加えて、C100h に値を書いて確かめます（8KB と 16KB を見分けるため）。書いた値はすぐに戻します。
- openMSX の ROM は書き込みを無視するので、システム ROM への書き込みがあっても検出しません。これは模擬環境の検査が見ています。

| リセットのたびに再生される | 確認済み | リセット 1 回の構成 |
| C-BIOS_MSX2、C-BIOS_MSX2+ で全項目に通る | 確認済み | `--machine` で 2 つのイメージとも |
| もう一方のページに別の ROM がある構成（C-BIOS_MSX1） | 確認済み | `--machine C-BIOS_MSX1 --rom neighbour`。ページ 1 用のイメージは全項目に通り、リセット後も再生される。ページ 2 用のイメージは INIT が呼ばれない |

### openMSX での動作（純正 BIOS）

`tools/test_openmsx.py --machine` で、Casio PV-7（RAM 8KB、スロット 0）、Sony HB-10（16KB、スロット 0）、National CF-2000（16KB、スロット 0）、Canon V-20（64KB、スロット 3、50Hz）、Sony HB-11（64KB、副スロット 3-2）を、2 つのイメージで試した結果。

| 項目 | 確度 | 確かめ方・補足 |
|---|---|---|
| 5 機種とも全項目に通る。INIT は 1 回呼ばれ、リセットのたびに再生される | 確認済み | ROM がミラーなし（既定）と、もう一方のページに別の ROM がある構成（`--rom neighbour`）の両方 |
| INIT から戻ったあと BASIC が起動し、`Ok` が表示される | 確認済み | PV-7、HB-10、CF-2000、V-20 |
| HB-11 では INIT から戻ったあと内蔵ソフトが起動する | 確認済み | 画面が SCREEN 2、page 1 がスロット 3-0。カートリッジなしの起動でも同じ（この ROM によらない本体の動作） |
| 主 RAM が BIOS と同じスロット 0 にある機種で、RAM 容量が正しい | 確認済み | PV-7（8KB）、HB-10、CF-2000（16KB） |
| 主 RAM がスロット 0 の別の副スロットにある機種で、RAM 容量が正しく、BASIC が起動する | 確認済み | HB-10 の RAM を `--ram` で置き換えた機種: 副スロット 0-2 に 64、48、32、16、8KB、副スロット 0-1 に 64KB。Canon V-20 を副スロット 0-2 に 64KB、Casio PV-7 を副スロット 0-3 に 8KB |

### 保証しない構成での動作

| 項目 | 確度 | 確かめ方・補足 |
|---|---|---|
| ROM がミラーされていると、純正 BIOS は INIT を 2 回呼び、アニメーションが 2 回再生されてから BASIC が起動する | 確認済み | openMSX の Sony HB-10 で `--rom mirrored`、2 つのイメージとも。段階の数が 308 |
| ROM がミラーされていても、C-BIOS_MSX1 は INIT を 1 回しか呼ばず、1 回だけ再生される | 確認済み | `--machine C-BIOS_MSX1 --rom mirrored`、2 つのイメージとも全項目に通る |

### blueMSX での動作

blueMSX+ 3.1.1 を起動して、ウィンドウの表示を 0.5 秒おきに取得して確かめたものです。機種定義は、Casio PV-7 の BIOS（openMSX の PV-7 のものと同じ内容）、RAM 8KB をスロット 0 に置いたもので、BIOS の ROM の種類を 1（書き込みでバンクが切り替わるマッパー）として登録してあります。

| 項目 | 確度 | 確かめ方・補足 |
|---|---|---|
| 2 つのイメージとも、`Main RAM :  8KB` を表示して BASIC が起動する | 確認済み | BASIC の画面に `4239 Bytes free` と `Ok` |
| blueMSX は 16KB の ROM を既定でミラーし、アニメーションが 2 回再生される | 確認済み | 上と同じ実行。保証しない構成 |
| ROM タイプを「Normal 4000H」（ページ 1 用）、「BASIC ROM」（ページ 2 用）にすると、ミラーされず、1 回だけ再生されて BASIC が起動する | 確認済み | 画面の操作で ROM タイプを選んで確認。設定ファイルで既定のカートリッジの種類を 42（ページ 1 用）、39（ページ 2 用）にした実行でも同じ結果。番号と画面上の名前の対応は確かめていない |
| この機種定義で BIOS の ROM の 0100h に値を書くと、0000h–1FFFh の内容が入れ替わる | 確認済み | 書き込みの前後で 0100h、000Ch、01B6h などの内容を画面に出す診断用の ROM で確認。RAM 容量の検査が BIOS のある page に書き込まない理由になっている |

### 確かめていないこと

| 項目 | 確度 | 補足 |
|---|---|---|
| 主 RAM がスロット 0 の副スロットにある、実在の機種の定義での動作 | 未実施 | 該当する配置は、派生させた機種でだけ確かめている。openMSX の機種定義では Yamaha AX150 / AX200、Daewoo CPC-51、Sony HB-F500、Victor HC-80 などが該当する |
| 純正 BIOS の MSX2 以降の機種 | 未実施 | MSX2 と MSX2+ は C-BIOS でだけ確かめている |
| ディスクドライブなど、作業 RAM を確保するほかの ROM と一緒に使ったときの動作 | 未実施 | 作業 RAM の E000h–E05Fh が、先に初期化されたほかの ROM の領域と重ならないことは確かめていない |
| HB-11 の内蔵ソフトが起動する仕組み（H.STKE のフック）と、スロット構成の違うマシン定義での挙動 | 未検証 | 「[内蔵ソフトを持つ機種](#内蔵ソフトを持つ機種)」を参照 |
| MSX 本体と BIOS の挙動についての記述のうち、副スロットレジスタの写しが実際の選択と合わない環境があること、割り込み処理が VDP のステータスを読むこと | 未検証 | 出典の記録がない |
| zmac、sjasmplus、Pasmo 以外のアセンブラ | 未実施 | |
