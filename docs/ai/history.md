ロゴの基準にした画像は、依頼者が提供した MSX2 起動画面のスクリーンショット（480×424）。リポジトリには入っていない。`tools/gen_assets.py` の頂点列はこの画像の座標で書かれている。

### v5: 8000h ミラーによる INIT の二重呼び出し

16KB の ROM は、多くのエミュレータ（openMSX の自動判定「Mirrored」など）や単純なカートリッジ基板で 8000h–BFFFh にも同じ内容が見える。BIOS の ROM 検索は各スロットの 4000h と 8000h の両方で AB 署名を調べるため、ミラーがあると INIT が 2 回呼ばれ、1 回目の RET のあと BASIC へ進まず、アニメーションがもう一度始まっていた。

対策: INIT の先頭で自スロットの 8000h / 8001h を RDSLT で読んでミラーを判定し、ミラーがある場合だけ 1 回目の終了時に D820h / D821h へ目印（5Ah、A5h）を書く。2 回目の呼び出しでは目印を消してすぐに RET する。

確認済み（検証プログラム）: ミラーありで 1 回目が目印を残し、2 回目が何も描かずに戻って目印を消すこと。ミラーなしで目印が残らないこと。

確認済み（openMSX）: 純正 BIOS の 4 機種（Sony HB-10、HB-11、National CF-2000、Canon V-20）は、ミラーがあると INIT を 2 回呼ぶ。2 回目は 1 回目の RET の約 2 ミリ秒後で、すぐに戻る。C-BIOS 0.29 は 1 回しか呼ばない。この違いから出る不具合は「2026-10-04 zmac 対応、ビルドスクリプト、openMSX テスト」の節に書いた。

### v6: 拡張スロットに RAM がある機種でのリセット

HB-11 のように主 RAM が拡張スロット（3-2）にある機種で、RAM 容量の検査の時点で暴走・リセットしていた。v5 までは主 RAM の副スロット番号を SLTTBL（BIOS の副スロットレジスタの写し）から求めていたが、この値が page 3 の実際の選択を反映していない環境では別の副スロット（例: 3-0）を指定してしまう。その状態で C100h を RDSLT / WRSLT すると、BIOS が page 3 の副スロットを切り替え、スタックとワークエリアのある RAM が消えて暴走する。

対策: 主 RAM の副スロットは FFFFh を直接読んで求める。page 3（C100h）の検査はスロット間呼び出しを使わず、直接読み書きする。

再構成前の README には「主 RAM を拡張スロット 3-2／3-1 に置いた構成（64KB・16KB）で v5 が暴走すること、v6 が正しい容量を得て RET することを確認した」とあった。

確認済み（検証プログラム）: SLTTBL にわざと古い値を置いた模擬構成（主 RAM が 3-2）で、正しいスロット ID で RDSLT / WRSLT が呼ばれること、page 3 のアドレスでは呼ばれないこと。

確認済み（openMSX）: 純正 BIOS の Sony HB-11（主 RAM が 3-2）と、C-BIOS の機種定義から RAM を 3-2（64KB、48KB）と 3-1（16KB）へ移した機種で、正しい容量を得て RET すること。

### v7: 作業 RAM を BIOS のスタックから離す

v6 までは作業 RAM が C000h–F047h 固定で、変数（F000h–F047h）が BIOS / BASIC のスタック（標準構成で F0A0h 付近から下向き）のすぐ下にあった。スタックがこれより低い機種では、変数への書き込みが呼び出し元（BIOS の ROM 検索）の退避データを壊し、RET のあとに暴走する。

対策: 表示用の画像バッファを C000h–D7FFh の 1 枚だけにし、変数を D800h 以降へ移した。D8A0h 以上には一切書き込まない。完成形の画像を RAM に写して持つのをやめ、レーザーを消すときは、その列が出現済みなら ROM の輪郭データ、未出現なら 0 で戻す。

確認済み（検証プログラム）: 終了時に D8A0h–F2FFh が書き換えられていないこと。

確認済み（openMSX）: C-BIOS と純正 BIOS の機種で、D8A0h から「INIT に入った時点のスタックポインタの 256 バイト下」までが INIT の前後で同じであること。

### v8: 終了時の作業 RAM の消去と HB-11

INIT の最後で作業 RAM（C000h–D89Fh）をすべて 0 に戻してから RET する（ミラー用の目印だけは残す）。

HB-11 の内蔵ファームウェアについての観察（H.STKE のフック、マシン定義によってはリセットを繰り返すこと）もこの版の説明にあった。内容は `docs/technical.md` の「内蔵ソフトを持つ機種」へ移した。ファームウェアを 3-1、RAM を 3-0 に置いたマシン定義では、フックが RAM の 5E60h に飛んで RAM の内容をコードとして実行し、この ROM のあとではリセットを繰り返す、という記述だった。

確認済み（検証プログラム）: 終了時に C000h–D89Fh が目印を除いて 0 であること。

確認済み（openMSX）: HB-11 では INIT から戻ったあと内蔵ソフトが起動する（画面が SCREEN 2、page 1 がスロット 3-0。カートリッジなしの起動でも同じ状態）。フックの仕組みそのもの（H.STKE、83h）は確かめていない。

### v9: RAM 容量の表示をシステムフォントに変更

`Main RAM : ##KB` を、自前のフォント画像（`text##.dat`）ではなく本体のシステムフォントで表示するようにした。作業 RAM に D826h / D827h（フォントのアドレス）を追加した。

確認済み（検証プログラム）: 代用フォントを CGTABL / CGPNT の指す位置に置いた環境で、文字のパターンが期待どおりの位置に転送されること。

確認済み（openMSX）: C-BIOS と純正 BIOS の機種で、表示された文字のパターンが、その機種の BIOS のフォントと一致すること。

- **ビルドの出力は `build/` に集め、追跡しない。**
- **`docs/images/preview.gif` は追跡し、検証プログラムの出力先は `build/` のままにする。** 理由: 検証のたびに追跡対象のファイルが書き換わるのを避ける。前提: 見た目の変更がまれで、手でコピーする手間が小さい。

## 2026-10-04 zmac 対応、ビルドスクリプト、openMSX テスト

再構成のあと、依頼者から次の情報と指示があった。開発機に zmac と openMSX があること。スクリプトにローカルのパスを書かず、実行ファイルの場所は環境変数（`ZMAC_EXE`、`OPENMSX_DIR` が定義済み）を経由すること。埋め草はビルド時にスクリプトで埋めてよいこと。純正 BIOS の ROM が手元にあり、使ってよいこと。

### 行ったこと

- ソースの末尾の埋め草（`ds 0x8000-$,255`）を外し、`tools/build.py` を追加した。アセンブラを環境変数、PATH の順で探して実行し、イメージを FFh で 16KB に埋め、シンボルを `build/symbols.json` にまとめる。ROM の内容は変わっていない（SHA-256 が同じ）。
- `tools/verify.py` がラベルを読む先を `build/symbols.json` にした。アセンブラごとのシンボル形式の解釈は `tools/build.py` に集めた。
- `tools/test_openmsx.py` と `tools/openmsx_test.tcl` を追加した。

### 確かめたこと

いずれも確認済み。zmac 18oct2022、sjasmplus 1.24.0、Pasmo 0.5.4.beta2、openMSX 21.0（C-BIOS 0.29）、Python 3.13.14。

- zmac は `ds 個数,埋め値` の埋め値が −128〜127 でないと Value error にする（`zmac.y` の DEFS の規則にその検査がある）。`0xff`、`0FFh`、`$ff`、`255` はどれも通らない。負の値（`-1`）は Phase error になる。埋め値なしの `ds` は、zmac ではイメージに出力されない。
- zmac は出力ファイルの拡張子で形式を決める。`.rom` は受け付けず、生のイメージは `.cim`。
- 埋め草を外したソースを 3 つのアセンブラでビルドすると、どれも 14,196 バイトのイメージになり、FFh で埋めた ROM は再構成前と同じ SHA-256 になる。シンボルも 3 つで一致する。
- openMSX は、スクリプトで `set renderer none` とするとウィンドウを開かずに動く。環境変数 `OPENMSX_USER_DATA` でユーザーデータのフォルダを切り替えられる。ファイルプールは、そのフォルダの `settings.xml` の `__filepool` に書いておけば、機種の読み込みに間に合う。
- openMSX は 16KB の ROM を自動で全ページにミラーする。`-romtype Normal4000` でミラーなしになる。
- `tools/test_openmsx.py` の結果は `docs/technical.md` の「検証状況」に書いた。純正 BIOS の機種は、依頼者の手元の ROM で起動できた Sony HB-10、National CF-2000、Canon V-20、Sony HB-11 の 4 つ。HB-11 のファームウェアは手元では 16KB ごとのファイルに分かれていたので、一時フォルダで 2 つずつ結合して、openMSX の機種定義が求める SHA-1 と一致するものを作った。副スロット 3-3 のぶんは、4000h 側が `dic5`、8000h 側が `dic4` の順で一致した。

### 見つかった不具合

ROM の動作の不具合で、どちらも直していない（依頼者の判断待ち）。`tools/test_openmsx.py` は意図どおりの動作を検査するので、直るまで不合格のままになる。

1. **C-BIOS の MSX1 機種で、ROM がミラーされているとき、リセット後は 1 回おきにしか再生されない。** C-BIOS 0.29 はミラーがあっても INIT を 1 回しか呼ばないので、目印（D820h / D821h）が消されずに残る。リセットで RAM が保たれると、次の起動の INIT が目印を見てすぐに戻る。4 回続けて起動すると、1 回目と 3 回目だけ再生された。C-BIOS_MSX2 はリセットのときに RAM が初期化されるので（INIT の入口で D820h / D821h が 33h 33h になっていた）、毎回再生される。
2. **純正 BIOS の機種で、ミラー経由の 2 回目の呼び出しのあと、D822h に自スロットの ID が残る。** 2 回目の呼び出しは、D822h に書いてから目印を調べ、作業 RAM を消さずに戻る。`tools/verify.py` は 2 回目の呼び出しのあとの D822h を見ていなかった。

再構成前の README には「openMSX 19.1＋C-BIOS で 2 回目の即時 RET を確認した」とあった。openMSX 21.0 の C-BIOS は 1 回の起動で INIT を 1 回しか呼ばないので、同じ観察は再現しない。当時見たものがリセット後の「すぐに戻る」起動だった、というのは未確認の候補で、openMSX 19.1 で同じテストを走らせれば決まる。

直し方の案（未実施。どれも ROM の内容が変わる）:

- 1 について: 目印に有効期限を持たせる。1 回目の終了時に JIFFY も保存し、次の入口で JIFFY との差が小さいときだけミラー経由とみなす。純正 BIOS では 2 回目の呼び出しは約 2 ミリ秒後で、リセット後の INIT は BIOS の初期化のあとなので、区別できる見込み（未検証）。
- 2 について: 2 回目の経路で D822h も消す。または自スロットの ID を RAM に置かずレジスタで持つ。

### 決定と前提

- **埋め草はソースに書かず、`tools/build.py` が FFh で埋める。** 理由: zmac が 128 以上の埋め値を受け付けない。0 で埋めれば 3 つとも通るが、ROM の内容が変わる。前提: ビルドに Python を使える。
- **ビルドのラッパーを置く（前の節の見送りを撤回）。** 理由: 埋め草の後処理が要る。zmac は出力の形式とシンボルの在りかがほかと違う。実行ファイルの場所を環境変数から受け取る必要があり、シェルごとの書き方の違いをスクリプトが吸収できる。見送ったときの前提（コマンド 1 行で済む）が成り立たなくなった。
- **シンボルは `build/symbols.json` にまとめる。** 理由: アセンブラごとの形式を知る場所を `tools/build.py` の 1 か所にする。
- **環境変数の名前。** `ZMAC_EXE`、`OPENMSX_DIR`、`MSX_ROM_DIRS` は依頼者の環境に既にあった名前。`SJASMPLUS_EXE`、`PASMO_EXE` は `ZMAC_EXE` にならって決めた。変えるときの波及は、`tools/build.py` の表と、`README.md`、`CLAUDE.md` の表。
- **openMSX テストは、ユーザーデータのフォルダを `build/openmsx/` に切り替えて動かす。** 理由: 利用者の openMSX の設定に触れない。機種定義を追加できる。前提: システム ROM の探索先を自分で `settings.xml` に書く（利用者のフォルダのファイルプールは見えなくなる）。
- **RAM の配置を変えた機種は、付属の C-BIOS の機種定義から実行時に作る。** 理由: openMSX の機種定義をリポジトリに写さない。前提: 定義の中のスロット 3 が `<primary slot="3">…</primary>` の形で 1 つだけある。

### 行ったこと

- 縦と斜めのレーザーをスプライト（16×16、拡大なし）にした。横のレーザーはパターンのままで、バイト単位で書く。画面を RAM に写して持つのをやめた。

- ソースを本体（`src/logo.asm`）と、`rom_base` を定義するだけの入口 2 つ（`src/page1.asm`、`src/page2.asm`）に分けた。自スロットを求めるビットとミラーを調べるアドレスを `rom_base` から計算するようにした。
- ミラーの判定を、AB 署名の 2 バイトから、INIT のアドレスを含む 4 バイトの比較に変えた。

- `tools/build.py`、`tools/verify.py`、`tools/test_openmsx.py` を 2 つのイメージに対応させた。検証の期待値を `tools/screen.py` に分けた。`tools/test_openmsx.py` に 8KB の構成 2 つと `--rom` を足した。

アセンブラ:

- zmac の `-Dsym` は sym を 1 に定義するだけで、値は渡せない。`-Pk=num` は `@@k` という zmac だけの書き方になる。
- 行頭の `名前 equ 値` と `include "src/logo.asm"`（ルートからの相対）は、3 つとも同じバイナリになる。
- zmac のリストは、`equ` の定数を `名前 =値 10 進` の形（桁数は可変）で出す。ラベルは `名前 4 桁 10 進`。`tools/build.py` の正規表現は両方に合う形にした。

openMSX:

- 16KB の ROM の自動判定は、ページ 2 用のイメージも全ページにミラーする。
- C-BIOS の機種はスロット 0 の 8000h に C-BIOS 自身のロゴ ROM を持ち、8010h が実行される。スロットの条件を付けないブレークポイントは、ページ 2 用のイメージの INIT と取り違える。
- C-BIOS_MSX1 は RAM が 8KB の構成でも起動する。INIT の時点で BOTTOM は E000h、HIMEM は F380h。
- `machine_info slot` は 16KB のページ単位でしか装置を返さない。8KB の RAM は page 3 の装置として返る。
- INIT に入った時点のスタックポインタは、純正 BIOS の 5 機種で F08Eh、C-BIOS で F2ECh。HIMEM はどちらも F380h。
- `OPENMSX_USER_DATA` が切り替えるのは設定と機種定義のフォルダだけで、時計チップや電池つき RAM の保存ファイル（`persistent/`）は切り替わらない。`OPENMSX_HOME` も向ければ切り替わる。MSX1 の機種には保存ファイルがないので、MSX1 だけを試している間は違いが出ない。
- C-BIOS_MSX1 は、同じスロットのページ 1 に別の ROM があると、ページ 2 の ROM の INIT を呼ばない。純正 BIOS の 5 機種は両方を呼ぶ。

### 決定と前提

- **縦と斜めはスプライト、横はパターン。** 理由: 67 ドットの横線は 1 走査線に 5 枚のスプライトが要る。縦と斜めは 1 本につき 1 走査線 1 枚で済む。前提: 同時に出るレーザーが 3 本まで。4 本以上にすると 1 走査線 4 枚の制限に当たりうる（生成時に検査して、超えればエラーにしている）。
- **スプライトの位置は生成時に計算して `beams.dat` に入れる。** 理由: はみ出しの扱い（座標が 8 ビットに収まらない、左端のアーリークロック、Y=208 を避ける）を ROM に持たずに済む。値段: `beams.dat` が 576 バイトから 1,148 バイトになった。前提: ROM に空きがある（現在 15,212 / 16,384 バイト）。
- **レーザーの長さは 67 ドットのまま。** 16 の倍数でないので終端用のパターンが 3 つ要るが、動きを変更前と同じに保つことを優先した。
- **色の切り替えは 2 フレームごと。** 依頼は「数フレームごと」で、2 はこちらの判断。60Hz では 1 段階（6 フレーム）で 3 色がちょうど一巡する。変えるときは、ソースの `color_frames`、`tools/screen.py` の `COLOUR_FRAMES`、文書の記述。フレーム数で数えるので、50Hz と 60Hz で速さが違う。
- **色の切り替えは締切方式にする。** tick と同じく JIFFY と締切を比べ、締切を 2 ずつ進める。理由: 描画が長引いても色がフレーム数に従う。待ちのループでは、tick の締切を先に調べ、そのあとで色を調べる。同じフレームに両方が来たとき、消す直前のレーザーを塗り直さないため。
- **画面を RAM に写して持たない。** 理由: 6KB の写しは 8KB の機種に置けない。写しが要ったのは、レーザーを 1 ドットずつ重ね書きするためだった。前提: パターンに描くのは横のレーザーだけで、1 つの段階の中で 2 本が同じバイトを使わない（生成時に検査している）。
- **作業 RAM は E000h–E07Fh。** 理由: どの MSX にもある RAM の先頭で、スタックから遠い。前提: この ROM より先に初期化されたほかの ROM が、E080h より下まで領域を確保していない。**この前提は確かめていない**（ディスクドライブの ROM などとの共存は未実施）。動かすときの値段は、ソースの `work` 1 つと、文書の表。
- **8KB の表示は `Main RAM :  8KB`（数字を右寄せ）。** こちらの判断。15 文字のまま位置を変えずに済む。変えるときは、ソースの文字列 1 つと、検証スクリプト 2 本の書式（`{kb:2}`）。
- **輪郭の 1 列の書き込みを連続書き込みにした。** 依頼にはないが、1 段階を 1 フレームに収めるために行った。前提: 連続書き込みの間隔が VDP の必要とする 8 マイクロ秒を超えている（`vram_out` を呼ぶ形で確保。模擬環境で最小 42 T）。
- **ミラーの判定は 4 バイトの比較。** 理由: ページ 2 用のイメージは、ページ 1 に別の ROM がある構成で使われうる。署名だけの判定ではそれをミラーと誤り、目印が残って、リセット後に再生されない。
- **イメージは入口のソース 2 つで分ける。** 理由: コマンドラインから値を渡す方法が 3 つのアセンブラで共通にできない。入口が定義するのは `rom_base` だけで、ページによる違いはすべてそこから計算する。ページを増やすときは、入口のソース 1 つと `tools/build.py` の `PAGES` に 1 行（ページ 0 と 3 は、自スロットの求め方が今の計算では合わない）。
- **検証スクリプトは既定で 2 つのイメージとも確かめる。** 理由: 片方だけ確かめて済ませる余地を残さない。
- **検証の期待値は、レーザーの形から組み立てる。** `beams.dat` のバイト列は使わない。理由: 符号化と、それを読む ROM の両方を確かめられる。色、間隔、矩形の範囲は、検証側が ROM から読まずに自分で持つ。理由: ROM の値を読むと、値を誤って変えても検査に通ってしまう。
- **スプライトの大きさの設定を元に戻す。** 理由: 画面モードを変えてもこの 2 ビットは保たれるので、戻さないと BASIC に 16×16 の設定が残る。
- **別の ROM がある構成は既定の構成に入れず、`--machine` と `--rom neighbour` で試す。** 理由: C-BIOS はページ 2 の ROM の INIT を呼ばないので、既定の構成（C-BIOS）に入れるとページ 2 用のイメージが必ず不合格になる。
- **openMSX は `OPENMSX_HOME` も `build/openmsx/` に向けて起動する。** 理由は上の観察のとおり。

## 2026-10-04 ミラー対策の削除、スロット 0 の RAM、blueMSX での調査

前の節の作業を報告したあと、依頼者から 2 つの連絡があった。「ミラーでの動作は保証しないでいいと思う」。「blueMSX の PV-7 の構成で、BASIC に進まず、メモリの検査のところでリセットしているようだ。念のため調査してほしい」。続けて「ページ 1 用は演出を繰り返し、ページ 2 用はメモリの検査で固まる」「違いはシステム BIOS くらいだと思うが、直接の原因は調べておきたい」。

この節の作業で、前の節に書いたことのうち次のものは**現在の ROM には当てはまらない**: ミラーの判定（4 バイトの比較）、目印、自スロットの判定、`--rom` の既定が `mirrored` であること、作業 RAM が E000h–E07Fh であること、既知の不合格が 2 種類あること。

### blueMSX の症状の原因

**依頼者の blueMSX の機種定義で、BIOS が ROM の種類 1 として登録されていたこと**が原因だった。種類 1 は、ROM の番地に値を書くとその 8KB の領域のバンクが切り替わるマッパーである。RAM 容量の検査は主 RAM のスロットの 0100h と 4100h に検査値を書く。PV-7 は主 RAM が BIOS と同じスロット 0 にあるので、そこは BIOS と BASIC の ROM で、0100h に書いた時点で BIOS の先頭 8KB が別のバンクに入れ替わっていた。

確かめた順序（いずれも確認済み）:

- openMSX に、blueMSX の定義と同じ構成（同じ BIOS ファイル、8KB の RAM をスロット 0、カートリッジをスロット 1 または 2）の機種を作ると、両イメージとも正常に動いた。BIOS の違いでは再現しない。
- 依頼者の定義の BIOS ファイルは、途中で差し替えられていた。最終的なものは、openMSX の Casio PV-7 の BIOS と SHA-1 が一致した。違いは ROM の種類だけになった。
- blueMSX+ 3.1.1 を一時フォルダに複製して起動し、ウィンドウの表示を連続で取得した。ページ 2 用のイメージは、青く塗り終えた約 0.8 秒後に、BIOS のロゴ画面を挟まずに先頭へ戻って繰り返していた。
- RAM 容量の検査の各手順の前に画面へ印を出して待つ診断用の ROM を作ると、検査値を書いたあとの最初の読み戻しのところで落ちた。書き込みを 1 つずつ外すと、0100h か 4100h への書き込みを外したときだけ、その場所を通過した。
- 書き込みの前後で ROM 領域の内容を画面に出す診断用の ROM で、0100h に 51h を書いた直後に、0100h が EEh から 10h（元の 2100h の値）へ、000Ch–000Dh が C3 B6 から 02 0C へ、01B6h–01B7h が CD 7E から 00 88 へ変わることを見た。4100h に 62h を書いても、見ていた番地は変わらなかった（62h の下位 2 ビットが、もとのバンクと同じ 2 だった）。
- 複製の機種定義で BIOS の種類だけを 20（通常の ROM）に変えると、当時の ROM でも両イメージとも BASIC まで進んだ。

落ち方が場合によって違った（先頭に戻る、リセットする、固まる）のは、BIOS が入れ替わったあとに実行されるのが意味のないコードだからである。途中で「0100h と 4100h の両方を書くと落ちる」ように見えたのも、その偶然だった。

### 調査で見つかった不具合と、依頼者の決定

**主 RAM が、拡張されたスロット 0 の副スロットにある機種で、RAM 容量の検査が暴走する。** 変更前の ROM にもあった。BIOS と同じ主スロットの page 0 に RDSLT / WRSLT を使うと、BIOS が page 0 の副スロットを切り替えた時点で、page 0 で動いている BIOS 自身が見えなくなる。Sony HB-10 の機種定義から RAM を副スロット 0-2 へ移した機種（純正 BIOS）で確認した（16KB でも 64KB でも、検査に入ったところで戻らない）。openMSX の MSX 系の機種定義 238 のうち 23 に、RAM がスロット 0 の副スロットにあるものがある。

依頼者に 2 点を尋ね、次のように決まった。

- **RAM 容量の検査は直す。スロット 0 の副スロットにある RAM も 64KB まで正しく数える。** 「page 0 を数えない」（64KB の機種が 48KB と表示される）と「直さない」は選ばれなかった。
- **ミラー対策のコードは削る。** 「コードは残して、保証しないと文書に書く」と「文書だけ」は選ばれなかった。ミラーされる構成ではアニメーションが 2 回再生される、と説明したうえでの選択。

### 行ったこと

- ROM から、自スロットの判定、ミラーの判定、目印を取り除いた。INIT は呼ばれるたびに再生する。前の節までの「見つかった不具合」2 件は、対象のコードがなくなって消えた。
- RAM 容量の検査で、page 0–2 の読み書きを `ram_read` と `ram_write` に通すようにした。主 RAM のスロットによって、RDSLT / WRSLT、調べない、ROM が副スロットを切り替えて直接、の 3 通りを page ごとに選ぶ（`docs/technical.md` の「RAM 容量の検査」）。
- 作業 RAM を詰めて E000h–E05Fh にした。
- `tools/verify.py` に、スロット 0 の RAM と副スロットレジスタの模擬、BIOS のある page への RDSLT / WRSLT と書き込みの禁止、BIOS を呼ぶ時点で page 0 に BIOS が見えていることの検査を足した。ミラーと自スロットの検査は外した。
- `tools/test_openmsx.py` の既定の構成をミラーなしにし、スロット 0 と副スロット 0-2 に RAM を置く構成を足した（16 構成）。機種の RAM を任意のスロットへ置き換える `--ram` を足した。`--rom` の既定を `alone` にした。
- `tools/test_openmsx.py` が openMSX を `OPENMSX_HOME` も切り替えて起動するようにした（前の節の観察のとおり）。

### 確かめたこと

結果の一覧は `docs/technical.md` の「検証状況」にある。ここには、そこに書かない観察を書く。いずれも確認済み。

- C-BIOS 0.29 は、ROM を副スロット 0-0、RAM を副スロット 0-2 に置いた機種でも起動する。変更前の方式（page 0 に RDSLT / WRSLT）に戻した ROM は、C-BIOS のこの構成でも落ちる。既定の構成がこの不具合を検出できることの確認になっている。
- 新しい ROM は、blueMSX の、BIOS を種類 1 として登録した機種定義のままでも、BASIC まで進む。
- blueMSX は、ROM のパスを引数にそのまま渡すと起動する。`/rom1` や `/machine` を付けると、blueMSX+ 3.1.1 はすぐに終了する（終了コード 1）。
- blueMSX は、設定ファイルの `cartridge.defaultType` で、引数で渡した ROM の種類を変えられる。20 では ROM が起動されなかった。42 でページ 1 用が、39 でページ 2 用が、ミラーなしで動いた。依頼者は画面の操作で「Normal 4000H」（ページ 1 用）と「BASIC ROM」（ページ 2 用）を選んで正常に動くことを確かめている。42 と 39 がその 2 つに当たるかは確かめていない（推測: 結果が一致する。blueMSX のソースにある種類の並びの記憶とも合う）。
- blueMSX の機種定義（`config.ini`）の `[Slots]` の行は、主スロット、副スロット、開始位置（8KB 単位）、長さ（8KB 単位）、種類、ファイル、の順。付属の定義では、BIOS は種類 20 か 66、RAM は 23。

### blueMSX を無人で観察する方法

blueMSX には、ウィンドウを開かずに動かす方法も、状態を外へ書き出す方法も見つからなかった。次の方法で観察した。

- 実行ファイル、設定、機種定義を一時フォルダに複製して、複製を起動する。設定ファイルは複製側のものが使われる。設定ファイルの中の絶対パス（機種定義や取り込み先のフォルダ）は、複製側を指すように書き換える。利用者の blueMSX の設定と履歴には触れない。
- 起動したプロセスのウィンドウを、PrintWindow（ウィンドウ自身の描画内容を取る API）で一定間隔に取得する。画面全体ではなくそのウィンドウだけを取るので、ほかのウィンドウは写らない。
- ROM の側で、手順ごとに画面へ印（タイルを 1 つ塗る）を出して 0.4 秒待つと、どこまで進んだかが取得した画像から数えられる。メモリの内容は、その値をタイルのパターンとして書けば、画像から読み戻せる。
- 利用者が blueMSX を起動している間は、複製を起動しない（先に確かめる）。

### 決定と前提

- **BIOS と同じスロットの page 0 と page 1 は、RAM として調べない。** 理由: そこは BIOS と BASIC の ROM である。書き込まなければ、機種定義が ROM をどう登録していても影響を受けない。前提: 拡張されていないスロット 0、または副スロット 0-0 の page 0 と page 1 が、システム ROM である。
- **スロット 0 の別の副スロットの page 0 は、ROM が副スロットレジスタを書き換えて直接読み書きする。** 理由: RDSLT / WRSLT が使えず、数えないと 64KB の機種が 48KB になる。前提: 割り込みを禁止していて、切り替えている間に BIOS を呼ばない。主 RAM の主スロットが 0 なので、page 3 から見える FFFFh がスロット 0 の副スロットレジスタである。
- **BIOS のスロットは EXPTBL の先頭（FCC1h）の bit 7 から求める。** 前提: BIOS がスロット 0、または副スロット 0-0 にある。
- **ミラーされる構成は保証しない。** 依頼者の決定。README には、エミュレータごとの ROM タイプの指定を書いた。
- **`--rom mirrored` は残す。** 理由: 保証しない構成で何が起きるかを確かめる手段になる。不合格になるのは仕様どおりで、`CLAUDE.md` にそう書いた。
- **blueMSX 用の自動テストは作らない。** 理由: ウィンドウを開くので無人の検証に向かない。観察の方法は上に書いた。

### 見送った提案

- **ミラー対策のコードを残す。** 見送った（依頼者の決定）。
- **スロット 0 の RAM の page 0 を数えない。** 見送った（依頼者の決定）。
- **RAM 容量の検査を、すべて自前のスロット切り替えにする。** 見送った。理由: 変更が大きい。必要なのは、RDSLT / WRSLT が使えない 1 つの場合だけである。
- **BOTTOM などの BIOS の変数から RAM 容量を求め、書き込みをやめる。** 見送った。理由: BIOS が持つのは page 2–3 の連続した RAM の下端だけで、48KB と 64KB を区別できない。
- **主 RAM がスロット 0 の副スロットにある実在の機種で試す。** 見送った。理由: 該当する機種のシステム ROM が手元にない。派生させた機種でだけ確かめている。

### レーザーの色の位相（同じ日の追加の指示）

依頼者から「3 本のラインが同時に同じ色にならないように、位相をずらしてローテーションする」という修正の指示があった。

- 同時に出る 3 本に 0–2 の番号を付け、番号ぶんだけ色の順番を進める。色の番号が 0 のとき、3 本は白、ライトイエロー、シアンになる。
- 番号は `beams.dat` に入れた。スプライトは、パターン名のバイトの下位 2 ビット（16×16 のスプライトでは VDP が無視する）。横のレーザーは、レコードの先頭に 1 バイト足した。`beams.dat` は 1,148 バイトから 1,179 バイトになった。
- ROM は、色が変わるたびに 3 本ぶんの色コードを作業 RAM に作り、スプライトと横のレーザーを書くときに番号で引く。
- 1 段階ぶんの処理は、平均 21,650 T から 22,937 T、最大 41,107 T から 42,084 T になった（模擬環境、60Hz で最大 0.71 フレーム）。
- 2 本のスプライトのレーザーが交わる点は、番号の小さいほうが手前に出る（スプライトを番号順に並べているため）。検証の期待値もそう作ってある。

この変更のあとで、アセンブラ 3 種の一致、2 つの検証スクリプト、純正 BIOS の機種、blueMSX、誤りを入れた ROM の試験（18 通り）を、すべて最終の ROM でやり直した。`docs/technical.md` の「検証状況」は、その結果である。

### blueMSX の ROM タイプ（依頼者の報告）

依頼者が、blueMSX で ROM タイプを「Normal 4000H」にするとページ 1 用が、「BASIC ROM」にするとページ 2 用が正常に動くことを確かめた。README の「使い方」の表は、この報告による。こちらでは、複製の設定ファイルで既定のカートリッジの種類を 42 と 39 にして、最終の ROM が 1 回だけ再生されて BASIC に進むことを確かめた（確認済み）。
